# Phase 10 design: volume snapshots (option B of design-phase10-snapshots.md)

Status: **decided with the user (2026-11-03); lab checks V1 to V11 done (section 7); built and unit tested on 2026-11-04 (`ProxmoxVolumeSnapshots`, section 9), not yet run on the lab.** The answers to the questions are in section 8. "V" means read in code (CloudStack in this repository, Proxmox in the mirrors under `promox-src`), "U" means unverified, with a lab check in section 7.

Instance snapshots (option A) are built and lab-verified. This document is about the other feature: the **volume snapshot** (`createSnapshot`, `Snapshot`, `SnapshotPolicy`), which copies a point in time of one volume to **secondary storage**, can be scheduled, and can create a volume or a template. Proxmox has no API for it (design-phase10-snapshots.md section 2), so the plugin does the work on the node with `qemu-img`, over the SSH login that Add Host stores (Phase 10).

## 1. What core sends, what KVM does, what Proxmox would do

Core uses `DefaultSnapshotStrategy` for every hypervisor (V). The commands are the same as for KVM; the plugin answers them.

| Step | Core sends (V) | KVM (V, `KVMStorageProcessor`) | Proposed for Proxmox |
|---|---|---|---|
| Take | `CreateObjectCommand(SnapshotObjectTO)` to a host | creates an internal qcow2 snapshot named by a random UUID on the volume's file; answers a path `<disk path>/<uuid>` | stopped or detached volume: `qemu-img snapshot -c <name> <file>`; volume of a running VM: a Proxmox VM snapshot (`vmstate=0`) named `cs-<uuid>` (section 3). Answer path `<volume path>/<name>` |
| Back up | `CopyCommand` snapshot on primary to snapshot on secondary (`NfsTO`) | `qemu-img convert` of the snapshot into a file on secondary, then **deletes the snapshot on primary** (`deleteSnapshotOnPrimary`) | `qemu-img convert -O qcow2 -l snapshot.name=<name> <file> <secondary>/<path>`, then delete the snapshot on primary, as KVM does. So the primary snapshot is transient and nothing stays in the data file |
| Delete | `DeleteCommand(SnapshotObjectTO)`; on secondary it goes to the secondary storage VM, on primary to a host | `qemu-img snapshot -d` | on primary: `qemu-img snapshot -d` or `DELETE .../snapshot/<name>`; on secondary: nothing in the plugin (core and the secondary storage VM remove the file) |
| Volume from snapshot | `CopyCommand` snapshot on secondary to `VolumeObjectTO` on primary | `qemu-img convert` into the pool | `qemu-img convert -O qcow2` into `images/<holder>/vm-<holder>-<volume uuid>.qcow2`, the same place and name as any data volume (behaviour.md section 20), answer the volume path |
| Revert | `RevertSnapshotCommand` (core allows it when the snapshot is on secondary, the volume is qcow2 (U: that the database has `QCOW2` as the format of a Proxmox volume, lab check V9) and the instance is stopped and has no instance snapshots, V `DefaultSnapshotStrategy.revertSnapshot`, `SnapshotManagerImpl`) | copies the secondary file over the volume | convert into a temporary file next to the volume, then `mv` it over the volume file, then `qemu-img resize` up to the volume's size in CloudStack when the volume was grown since the backup (section 5) |
| Template from snapshot | `CopyCommand` snapshot to `TemplateObjectTO` | convert, write `template.properties` | **not in this round** (section 6) |
| Scheduling, limits, usage | core | core | nothing to do: they call the commands above |

Which endpoint gets each command is chosen by core's default selection for a hypervisor other than KVM (`DefaultEndPointSelector.select`, V: the special routing in `getEndPointForSnapshotOperationsInKvm` is for KVM only). It has to be a Proxmox host that reaches the primary storage; for anything on the secondary store core may pick the secondary storage VM or a host (U, check in the log, lab check V9).

## 2. The mechanics on the node

All of it is `qemu-img` (and `mv`, `rm`, `mkdir`) run as the SSH user, with `sudo` when that user is not root (`ProxmoxSsh.sudo`). The paths:
- primary: `/mnt/<pool uuid>/images/<vmid or holder>/<file>` (read from `GET /nodes/<node>/storage/<id>/content` or the volume's `path`, which the plugin already uses: `ProxmoxApiClient.getImageInfo`);
- secondary: a mount of the NFS export read-write that the plugin makes over SSH when it is needed (section 5).

`qemu-img` runs on one node and the file is on shared NFS, so any node works; the plugin uses the node of the resource that got the command.

## 3. A volume that a running instance uses

**Decided: volumes of running instances and detached volumes are both in this round.**

`qemu-img snapshot -c` on a file that QEMU has open is not safe. A volume of a running instance therefore needs the VM to make the snapshot:
- **Proposed:** a Proxmox VM snapshot with `vmstate=0` named `cs-<uuid>`, which snapshots every disk of the VM (instance snapshots already work this way). The backup then reads **only that snapshot** of the one volume's file (`qemu-img convert -U -l snapshot.name=<name>`, `-U` because the file is open), which is safe because the clusters of a snapshot are never written (U, lab check V2). The VM snapshot is deleted right after the backup (transient), so `move_disk delete=1` (refused while a snapshot exists) and CloudStack's own checks see nothing left over.
- The snapshot of the other disks of the VM is a side effect: some seconds of extra work and an entry in the VM's snapshot list for the length of the backup. A failure in between leaves a `cs-<uuid>` snapshot; `ProxmoxVmSnapshots.deleteAll` removes it when the instance is expunged, and the delete command removes it when CloudStack deletes the snapshot.
- Core refuses a volume snapshot while the instance has a snapshot **with memory** (V `validateVmSnapshot`), and refuses a revert while it has any instance snapshot. Both stay as core has them.

A stopped instance or a detached volume needs none of this: `qemu-img snapshot -c` directly.

## 4. The SSH login in the resource (what must be built first)

The resource (`ProxmoxResource`) has no login today. `host_details` keeps `sshuser`, `sshpassword` (encrypted by the plugin **only when the management server's database encryption is on**; in a lab without it they are plain text, as every password in the database) and `sshfingerprint` (Phase 10), and the management server's private key is the hidden global setting `ssh.privatekey`. Proposal: `ProxmoxServerDiscoverer` puts the login, the key and the fingerprint into the resource's parameters at every connect, as it already does for the API token, and the resource builds an `SshTarget` from them (key first, then password, pinned fingerprint: the same `ProxmoxSsh` that Add Host and Update Host password use). They live in the management server's memory only, next to the API token secret that is there already. After `updateHostPassword` the new login must reach the resource at its next reconnect (it does for the token; U for this).

**Security of the login in the resource.** The login adds no storage and no network exposure: the password is already in `host_details`, the key is the existing hidden setting `ssh.privatekey`, and the resource runs in the management server's JVM next to the API token secret (neither `ResourceManagerImpl` nor the plugin logs the resource's parameters, read in code). What changes is the strength of what is in memory: the API token is limited by the Proxmox roles, the SSH login is root (or a sudo user) on every node, so a heap dump of the management server shows more than before, as it does for the login of a KVM host. **Passwords are in the database as plain text unless database encryption is switched on** (`DBEncryptionUtil` returns its input otherwise): production needs it on, for the SSH password, the token secret and the key alike. The real risk of this feature is command injection: the commands put CloudStack strings (the volume path, the snapshot name, the secondary store URL) into a root shell. Every value is checked against a strict pattern before it is used (UUIDs; paths of `[A-Za-z0-9/._-]` only; the NFS server and export from the store's URL) and anything else is refused, and the existing `ProxmoxSsh.quote` is used on top of it. When the SSH user is not root, every command runs as `sudo sh -c '<command>'` (`ProxmoxSsh.sudo`), so a `sudoers` entry that names single programs is not enough and the user needs full `sudo` (`NOPASSWD: ALL`, or the password in Add Host); limiting `sudo` to some programs would need a different way of running the commands (corrected on 2026-11-04, the earlier text said it could be limited).

## 5. Secondary storage, sizes and revert

- **A secondary mount, made by the plugin for the one operation (changed 2026-11-05; the first version mounted `/mnt/css-rw-<hash>` once and left it mounted).** The plugin mounts the secondary store's NFS export over SSH, in a directory of its own (`/mnt/css-tmp-<random>`), read-write to back a snapshot up and read-only to read one, with the options of the setting `proxmox.secondary.mount.options` (default `soft,timeo=30,retrans=2,nosharecache`), and unmounts and removes it afterwards (behaviour.md section 24, design-phase11-secondary-mounts.md). It is not a Proxmox storage entry. The export must let the node's root write to it (`no_root_squash`, as for KVM). Mounting the same export a second time next to the Proxmox entry works (lab V3) and, with `nosharecache`, gets options of its own.
- **Sizes.** The answers carry the virtual size and the physical size (`qemu-img info`), as KVM does.
- **Sizes (lab checks V6 and V11).** `qemu-img convert -l snapshot.name=` writes the volume's **current** virtual size, and the area added since the snapshot is empty. That cannot happen between a take and its backup through CloudStack: core refuses a resize while a snapshot is not backed up yet, and the plugin takes the snapshot, backs it up and deletes it from primary in one go. So **the backup has the size the volume had at the snapshot**, and:
  - **revert** keeps the size of the backup (corrected on 2026-11-05, see decision 5): core sets the recorded size of the volume to the size of the snapshot after a successful revert (`SnapshotManagerImpl.updateVolumeSizeAndPrimaryStorageCount`: the size, the primary storage count and a resize usage event), so the file must have that size; a volume that was grown after the snapshot is the smaller size again, as with KVM, where the old file is simply put back;
  - **volume from snapshot** is brought to the size of the new volume (`VolumeObjectTO.getSize()`): grown when the offering is bigger, and cut with `qemu-img resize --shrink` when it is smaller, which only happens after a check with `qemu-img map` that nothing is stored beyond that size (V11 shows it is empty); with data beyond it the command fails and nothing is cut. In practice the cut is never needed, it is a guard for a size that CloudStack records wrongly.
- **No note in the UI** (decision of 2026-11-04): the snapshot's API record has no `hypervisor` field (V10), so a note for Proxmox volumes only is not possible without extra work; the behaviour is in behaviour.md.
- **Failures.** A convert that fails removes its partial file on secondary; the primary snapshot is removed in a `finally`; nothing is deleted before the new file is complete (revert uses a temporary file and `mv`).
- **Locking.** One lock per volume path in the plugin, as the holder locks.

## 6. Not in this round

- **Template from snapshot.** It writes a template and its `template.properties` on secondary, which overlaps the template and ISO layout redesign (a later round). It stays unsupported for Proxmox, with the clear text of the answer.
- Incremental snapshots, snapshots of encrypted volumes, group snapshots.
- Moving a volume that has snapshots on secondary: the snapshots are on secondary, not in the file, so the move works as it does now.

## 8. Decisions (2026-11-03)

1. **Scope:** take, back up, delete, **create volume from snapshot** and revert. **Template from snapshot** is not in this round (open-issues.md, "Later work").
2. **Volumes of running instances and detached volumes both work** (section 3).
3. **The SSH login in the resource parameters is acceptable;** the points of section 4 (command injection checks, database encryption in production, limited `sudo`) go with it.
4. **The plugin mounts the secondary store read-write over SSH when needed and does not mount it again when it is mounted** (section 5), instead of a second Proxmox storage entry.
5. **Revert keeps the size of the backup and does not resize** (corrected twice: V6 first suggested no resize; on 2026-11-04 it was changed to grow the copy to CloudStack's current size, which was wrong; corrected on 2026-11-05 after SM2 on the lab). Core sets the volume's recorded size to the snapshot's size after a successful revert, so growing the file first left a 10 GiB file recorded as 5 GiB, and every later snapshot of the volume then had a 10 GiB backup with a 5 GiB record, which a "create volume" refused to cut because the upper half held data. VS6 had been passed on the size of the file alone; it must also compare with the database (`volumes.size`). **No note in the UI** (decision of 2026-11-04): the snapshot record has no hypervisor field, so the behaviour is documented in behaviour.md only.
6. **A copy that is bigger than the size CloudStack records for a new volume is cut to it** with `qemu-img resize --shrink` (decided with the user on 2026-11-04, after V11 showed the area is empty), but only after `qemu-img map --output=json` shows no data beyond that size; otherwise the command fails with a clear message and nothing is cut.

## 9. What was built (2026-11-04)

- `ProxmoxVolumeSnapshots` (resource package) answers `CreateObjectCommand`, `CopyCommand` (primary to secondary and secondary to volume), `DeleteCommand` and `RevertSnapshotCommand` for a `SnapshotObjectTO`; `ProxmoxResource` sends them there. Everything runs over SSH through `ProxmoxSsh.sudo`; the Proxmox API is used only for the VM snapshot of a running instance and to find the VM.
- The SSH login reaches the resource as the parameters `ssh.login.user`, `ssh.login.password` and `ssh.login.key` (`ProxmoxServerDiscoverer.discover` and `buildConfigParams`, from the host details and the setting `ssh.privatekey`); an `updateHostPassword` that the node accepts replaces the login in the running resource at once. A host without a stored host key fingerprint is refused with the text to delete the host and add it again.
- Every value that CloudStack gives is checked before it reaches a shell: volume path `<digits>/vm-<digits>-<letters, digits, ->.qcow2`, pool uuid, snapshot name `[A-Za-z0-9-]{1,40}`, folders on secondary `[A-Za-z0-9._-]` with no `.` or `..`, NFS server and export, NFS version; then each is quoted. Unit tests refuse paths with `;`, `&&`, `..` and the like before any command runs.
- A delete of a snapshot on the secondary store is not handled by the plugin (core sends it to the secondary storage VM); the answer says so. Template from snapshot answers "not supported".
- Not done: unmounting the secondary directory (it stays mounted until the node reboots), an own sudo wrapper for limited sudoers (needs full sudo, section 4).
