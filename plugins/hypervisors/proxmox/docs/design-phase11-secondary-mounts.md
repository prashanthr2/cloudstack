# Phase 11 design: templates and ISOs read from a plain secondary mount (no storage entries)

Status: decided 2026-11-05 and revised the same day after the lab (items 1 and 5 changed, section 6; step 2 changed to option C, section 7); **step 1 of section 7 built, unit tested and lab verified 2026-11-05 (SM1 to SM5, SM7; test-log.md); step 2 built and unit tested 2026-11-05, lab checks TV1 to TV10 not yet run**; M2b and M3 pass (a shared `dir` entry with bind-mounted ISO files, section 6); M2b, M3 to M6 pass; nothing built yet. Replaces the per-account `cst-` and per-ISO `csi-` storage entries (design-phase3 4.1, design-phase6) and the whole-store `css-` entry.

## 1. Why

- Today every account whose templates are used gets a `cst-<account>` entry and every ISO a `csi-<hash>` entry in Proxmox's `storage.cfg` (open issue 8: never removed). They exist only because Proxmox lets a **token** use a file only as a volume of a storage entry (an absolute path is for `root@pam`; design-phase3 section 3).
- The plugin now has an SSH login with sudo (design-phase10-ssh-access.md), which can do the root-only part.
- **A secondary store that goes down must not affect the Proxmox nodes.** An NFS storage entry is polled by Proxmox's own daemons (`pvestatd`, the web UI, `pvesm status`); with a `hard` mount a dead export leaves those processes in uninterruptible sleep and the node shows as unavailable. The existing `css-` entry and the `css-rw-` mount (volume snapshots) are `hard` mounts today.
- KVM and VMware mount the secondary store on demand on the host that needs it (`KVMStorageProcessor.attachIso` through `getStoragePoolByURI`; `VmwareResource.prepareSecondaryDatastoreOnHost`, one datastore per store) and leave it mounted. Neither has Proxmox's cluster-wide, polled entry.

## 2. Decision (2026-11-05)

1. **No Proxmox storage entry points at the secondary store** (no `css-`, `cst-`, `csi-`): Proxmox's daemons never poll an NFS export of it. The one entry that stays is a small **local** `dir` entry `shared 1`, content `iso`, for the ISOs (item 5); it is not NFS and is polled like `csp-`.
2. **A plain NFS mount over SSH, on demand, per node**, in one place for templates, ISOs, volume snapshots and later template creation: `/mnt/css-rw-<uuid of server:export>` today (to be renamed or split, see 5). Read-only for reads, read-write only where the plugin writes.
3. **Mount options for a dead export that return an error instead of hanging**, from a global setting with the tested default (section 8): `soft,timeo=30,retrans=2,nosharecache`, plus `ro` or `rw` and the store's `vers=` set by the plugin. Every command that touches the mount runs under `timeout` (`mountpoint -q`, `qemu-img`, `ls`).
4. **Templates (changed to option C on 2026-11-05, section 7 step 2):** at the copy to primary the plugin mounts the store, checks the image (no backing file, no data file: the template is untrusted), converts it into a Proxmox template VM on the pool, and every root volume is a clone of it, so a deploy needs neither SSH nor the secondary store; linked clones are design-phase12.
5. **ISOs:** Proxmox accepts a CD drive only as a volume of a storage entry (a plain path is refused, also for root: section 6, M2). So the plugin **bind-mounts the single ISO file** from the plain mount onto `<csiso path>/template/iso/<name>.iso` on the node, and attaches `csiso:iso/<name>.iso` **through the API** (a token may use a volume of a storage). `csiso` must be `shared 1`, or Proxmox sees the ISO as a local disk and refuses an online migration. The bind is made, and checked, before the attach (Proxmox does not check that the file exists when it hot-attaches). When the ISO is detached and no VM on the node uses it, the bind is unmounted and the empty file removed; the plain mount stays while a bind uses it.
6. **Migration:** `PrepareForMigrationCommand` (destination) mounts the stores of the VM's ISOs there first, as KVM does; the path must be the same on every node.
7. **HA and node restarts (accepted gap):** when Proxmox itself restarts a VM that has an ISO attached on a node without the mount, or after a reboot, the VM does not start until the ISO is detached. CloudStack-started VMs get the mount in the start command. To be documented in behaviour.md when built; for a VM CloudStack starts, an ISO whose mount cannot be made is ejected with a log line rather than failing the start (to confirm when designing the start).
8. Strings from CloudStack reach the root shell only as validated paths and slot names (same rule as volume snapshots: regex, `ProxmoxSsh.quote`).

## 6. Lab results

- **M1 pass (2026-11-05):** `mount -t nfs -o ro,soft,timeo=30,retrans=2,nosharecache,vers=4.2` works with sudo; `findmnt` shows `ro` and `soft`; the lab's secondary export lies below the primary's export and `nosharecache` gave it its own mount.
- **M2 fail: Proxmox refuses a plain path for a CD drive, also from `root` on the command line.** `qm create 9001 --ide2 /mnt/mtest/template/tmpl/2/212/<file>.iso,media=cdrom` gives `ide2: unable to associate path '...' to any storage`. Source (`qemu-server` `cleanup_drive_path`, `pve-storage` `path_to_volume_id`): a path other than `/dev/...` is turned into a volume id, which works only for a file inside the `iso` directory of a **storage entry** (`<storage path>/template/iso/<name>.iso`, no folder below it), and the path is resolved with `abs_path` first, so **a symlink does not help** (it resolves to the real path). The earlier remark that an absolute path is "for `root@pam` only" was about `import-from` and does not carry over to the drive of a CD. So decision 5 (attach with `qm set <path>`) does not work, and decision 4 (templates) is not affected: a template is converted into `images/<vmid>/` and attached by its volume id.
- **Way forward to test (M2b): bind-mount the single ISO file** onto a file named `<name>.iso` in the `iso` directory of a **local `dir` storage** (the node's `local` entry, or one `dir` entry made by the plugin as it does for `csp-`), then attach `<storage>:iso/<name>.iso`. A bind mount is a real path, so `abs_path` leaves it alone. No NFS storage entry, nothing polled over NFS; one bind mount per ISO in use and per node, removed when the ISO is detached. Same HA and reboot gap as before (a bind mount is lost on a reboot). Other ways, and why not: a loop device (`/dev/loopN`) is accepted but is not on another node and not after a reboot; QEMU `args` bypasses Proxmox's management of the drive (no eject through Proxmox); copying the ISO to the local directory has no dependence on the secondary store afterwards but costs disk space on every node.
- **M2b pass (2026-11-05):** a bind mount of the ISO file onto `<local dir storage>/template/iso/<name>.iso` is accepted as `<storage>:iso/<name>.iso` (`pvesm list` shows the real size, 2,126,512,128 bytes). A VM with it attached starts, the drive can be ejected (`none,media=cdrom`) and attached again while the VM runs, and QEMU holds the file open (`/proc/<pid>/fd` shows the path in the storage directory). `qm set` accepts a drive whose volume does not exist (no check when hot-attaching), so the plugin must make the bind first and check `pvesm list`/the file before it attaches.
- **`local` does not work for migration:** it is a node-private storage, so Proxmox treats the attached ISO as a local disk and refuses an online migration ("can't live migrate attached local disks without with-local-disks option"). Whether the bind was on the destination made no difference.
- **M3 pass with a dedicated shared entry:** `pvesm add dir csiso --path /var/lib/cloudstack-iso --content iso --shared 1` (one entry for the cluster; `shared 1` tells Proxmox every node has the same files, so nothing is copied) and the same bind mount of the ISO on both nodes: online migration pve3 to pve1 and back works (9 s, downtime 4 to 5 ms), and instance snapshots with and without memory work with the ISO attached. So decision 6 stands: before a migration the destination must have the same bind (`PrepareForMigrationCommand`), at the same path. A missing bind on the destination is not seen by Proxmox's check (not tried).
- **Consequence for the design:** decisions 1 and 5 change. Secondary storage still has no NFS storage entry; there is **one small local `dir` entry `shared 1` (like `csp-`) for the bind-mounted ISOs**, plus per-ISO file binds from the plain `soft` mount. Item 5 becomes: the plugin makes the bind and attaches `csiso:iso/<name>.iso` through the API (a token may use a volume of a storage), so the ISO attach no longer needs `qm set` over SSH; SSH is needed only for the mounts and binds.
- **M4 pass (2026-11-05), with a long stall:** a separate NFS server (pve1, `/srv/nfstest`) mounted on pve3 with `ro,soft,timeo=30,retrans=2,nosharecache,vers=4`, one file bound into `csiso`, attached to a running VM. With all NFS traffic from pve3 dropped (`iptables DROP`, the worst case: no reset) for several minutes: `pvesm status`, `pvesm list csiso` and `qm status` answered every time (checked every 7 s, none failed or stalled), `pvestatd`, `pvedaemon` and `pveproxy` stayed active, the VM kept running, and a reader killed by `timeout` died (no uninterruptible hang). **A read of an uncached part of the file returned an error after 99 s** (`nfs: server ... not responding, timed out` in `dmesg`), not within the 30 to 60 s expected from `timeo` and `retrans`: so a guest's CD read stalls for about 100 s and then gets an I/O error. Reading attributes of a bound file that was already cached did not stall. To tune at build time: shorter `timeo`/`retrans`, and NFS version 3.
- **M5 pass (2026-11-05):** template 3 (the system VM template; 5,242,880,000 bytes virtual, 1.67 GiB on disk) converted from the `soft` read-only mount into `<primary>/images/9002/vm-9002-disk-0.qcow2` with plain `qemu-img convert -O qcow2` in **29.9 s** (both on the same NFS server in this lab); `qm create 9002 --scsi0 <pool>:9002/vm-9002-disk-0.qcow2` accepts the disk and the VM starts. No baseline for the old `import-from` of the same template was measured; to try at build time: `-m`, `-W` (parallel and out of order writes), which are safe for a new target file.
- **M6 pass (2026-11-05):** `qemu-img info --output=json` shows `backing-filename` / `full-backing-filename` for an image with a backing file and `format-specific.data.data-file` (and `data-file-raw`) for one with a data file, so the plugin can refuse both. The same JSON of the system template shows a second, nested `virtual-size` (522,649,088) that is not a backing file: to look at the whole `qemu-img info` output of a template when building the check, so it does not trip on nested objects.

## 7. Build plan

Nothing here is built. Steps 1 to 3 are in the order proposed on 2026-11-05 (**to confirm**: templates first, then ISOs and migration, then template from volume and snapshot). Each step ends with unit tests, lab checks, `behaviour.md` / `test-log.md` / `upstream-notes.md` entries, and a commit only when asked. Core is not touched.

### Step 1: the foundation (built 2026-11-05, lab verified the same day)
- **New class `ProxmoxSecondaryMounts`** (resource package), taking the `ProxmoxSsh` login like `ProxmoxVolumeSnapshots` does. It holds what `ProxmoxVolumeSnapshots.mountSecondary` does today and replaces it:
  - `withMount(ssh, NfsTO, readOnly, action)`: makes a **mount directory of its own for this one operation** (`/mnt/css-tmp-<random uuid>`), mounts the store there (`timeout 60 mount -t nfs -o <options of section 8> server:export DIR`, `vers=` from `NfsTO.getNfsVersion()`), runs the action, and in a `finally` unmounts (`timeout 30 umount DIR || timeout 30 umount -l DIR`) and removes the directory. Nothing is shared between operations, so there are no locks and no "already mounted" cases; **nothing stays mounted when an operation is over** (a dead export can only hurt an operation that is running); and the `css-rw-` mount of volume snapshots that was never unmounted is gone. A cleanup the first time the mounts are used after the host connected (the resource is rebuilt at a reconnect) removes directories `/mnt/css-tmp-*` older than 10 minutes that a crash left behind (lazy unmount if still mounted). Decided 2026-11-05.
  - A mount made by the old code (`/mnt/css-rw-*`, `hard`) is not used any more and stays until the node reboots or someone unmounts it (upgrade note).
  - `checkImage(ssh, file)`: `timeout 60 qemu-img info -U --output=json`, parsed with Jackson: accepts format `qcow2` or `raw`; refuses a `backing-filename` / `full-backing-filename`, a `format-specific.data.data-file`, and an unknown format; returns the virtual size. Only the top-level keys are read (the system template's JSON has a nested `virtual-size`, M6).
  - Validation as for volume snapshots: server, export, version, and the relative path (regex, no `.` or `..`) before they reach the root shell, then `ProxmoxSsh.quote`.
- **Two settings in `ProxmoxConfig`:** `proxmox.secondary.mount.options` (section 8) and, in step 3, `proxmox.iso.path`.
- **`ProxmoxVolumeSnapshots`** switches to the new class (its rw mount gets the same options) and its tests follow.
- Unit tests: option validation (allowed names and values, rejected `ro`, `rw`, `vers`, shell characters, empty), the mount command, an existing mount, the image check (qcow2, raw, backing file, data file, nested `virtual-size`, unknown format, command failure and timeout).

### Step 2: templates as Proxmox template VMs (option C, decided 2026-11-05; built and unit tested the same day, 658 plugin tests pass)

Revised on 2026-11-05. The first version of this step (the store address in the path, a convert per deploy, option A) was dropped for **option C**, because linked clones are wanted (design-phase12-linked-clones.md): the template is made once per pool as a Proxmox **template VM**, and every root volume is a clone of it. KVM caches the template on primary for the same reason (a backing file must be on the same storage).

**What core does with `template_spool_ref`, which the plugin must honour** (read from `VolumeServiceImpl`, `TemplateManagerImpl`, `StorageManagerImpl`):
- A row per pool and template. Core copies a template to a pool **under a database lock on that row** (`acquireInLockTable`), so one copy per pool and template runs at a time, also across management servers; other deploys wait and then see the row `Ready` and skip the copy. No lock of our own is needed for the copy.
- The `path` of the answer to the copy is stored as `install_path` (and the size as `template_size`) and **handed back in every later deploy** as the path of the `TemplateObjectTO` on primary. It is the only thing the deploy knows: it does not know the secondary store.
- A row that is `Ready` means the template is on the pool. If the plugin loses the template (an administrator deleted the template VM), the deploy fails with a message that says what to do (as KVM does with a missing base file); it is not made again, because the path no longer says where the template came from (see the decision on the path below).
- **Eviction** of an unused template from a pool (the storage garbage collector, `storage.cleanup.enabled` and `storage.template.cleanup.enabled`) sends a legacy **`DestroyCommand`** (not a `DeleteCommand`) with the pool and the stored `install_path`, and removes the row only when the answer is a success; a failure is retried at the next cycle. The plugin has no handler for it today (it answers "unsupported", so templates are never evicted). A template counts as in use while any volume that is not destroyed uses it on the pool (`isAnyVolumeActivelyUsingTemplateOnPool`), so a base with clones is not evicted by core; Proxmox refuses to delete a base that has linked clones as a second guard.

**The path** stored in `template_spool_ref.install_path` (and `local_path`, which core fills with the same value): **where the template is on the primary storage**, as on KVM (decision of 2026-11-05 after the first lab run, which had put the secondary location there). On KVM both columns hold the name of the template file in the pool, the same for full and linked clones (`KVMStorageProcessor` answers `primaryVol.getName()`, `TemplateObject` stores it in both columns; linked clones only change how the root volume is made from it). Here it is the base disk of the template VM in the pool: `<vmid>/base-<vmid>-disk-0.qcow2`, for example `104/base-104-disk-0.qcow2`, the form of a volume path. The first design put `secondary:<version>|<server>|<export>|<file>` there, so that a lost template VM could be made again; that is given up: a missing template VM fails the deploy as a missing base file does on KVM.

**The template VM**: named `cs-tmpl-<uuid of (pool uuid, source key)>`, where the source key is the NFS version, server, export and file of the secondary store; the name is only used by a repeated copy to find the VM it made before (core keeps no other record then). The deploy and the `DestroyCommand` find the VM by the id in the path and check that it is a template named `cs-tmpl-...` whose `scsi0` is `<pool entry>:<path>`; anything else (no such VM, or the id was given to another VM since) is "not there". No network, never started; one blank disk of the template's size that is replaced by the converted image (as the revert of a volume snapshot replaces a file); then `POST .../template`. Templates are skipped by the VM sync already (behaviour.md, section 3).

- **`copyTemplateToPrimary`** (core's lock is held): over SSH, mount the store read-only, check the image (`checkImage`), find the template VM by name; reuse one that is a template, destroy one that is not (a copy that crashed halfway), else make it: VM id from `nextid`, create the VM with a blank disk of the image's size rounded up to whole GiB, `qemu-img convert -O qcow2` into `<disk>.tmp` and `mv -f` over the blank disk, `template`, then read the base disk from its configuration. Answer: that path, the virtual size, the physical size. Any failure destroys the VM and removes the temporary file.
- **`createRootVolume`**: for a path of this form, find the template VM by the id in the path (a failure with what to do if it is missing); clone it with `POST .../qemu/<template vmid>/clone` (`newid` from `nextid` with the existing "id taken" retry, `name` = the instance's VM name, `full=1`, `target` = this node, `storage` = the volume's pool, `format=qcow2`), wait for the task, then the existing steps (grow the disk to the volume's size, answer the short path). A failure destroys the new VM. **No SSH and no secondary store in a normal deploy.** `full=1` is a copy made by Proxmox; `full=0` (linked) is design-phase12.
- **`DestroyCommand`** (eviction): finds the template VM by the id in the path (checked as above), destroys it (Proxmox refuses while clones depend on it: the answer is a failure with Proxmox's text, so core keeps the row and retries); a template VM that is gone (or whose id another VM has now, which is left alone), or a legacy `cst-` path, is a success.
- **Legacy paths** (`cst-<hash>:<id>/<file>`, copied before this change): `createRootVolume` still imports from the entry while it exists (the old `import-from`), otherwise the existing message; `DestroyCommand` answers success without doing anything. No new `cst-` entries are made.
- **Removed:** `createTemplateDirStorage` and its tests, the use of `cst-` entries for new templates. The `css-` entry and `ensureSecondaryMount` stay for ISOs until step 3.
- **New client calls:** `cloneVm`, `convertToTemplate`, and a way to read the `template` flag of a VM configuration. The token needs `VM.Clone` and `VM.Allocate` as well (to confirm on the lab; `PVEVMAdmin` has them).
- Unit tests: the path form (every refusal), the source key, the name, the copy flow with the scripted SSH link and the mock client (new, reused, half-made, each failure with its clean-up), the deploy (clone parameters, "id taken" retry, missing template VM fails with what to do, the grow, the clean-up), `DestroyCommand` (found, gone, refused by Proxmox, legacy), the legacy deploy, and the dispatch of `DestroyCommand`.
- Lab checks: deploy from the system VM template and from a user template, a second deploy (no SSH, no mount: check the sudo journal), the template VM visible in Proxmox as a template, a template with a backing file refused, delete the template VM by hand and deploy again (fails with the message; remove the row and deploy: copied again), eviction (`DestroyCommand`) of an unused template and of one with an instance, parallel deploys, an existing instance still starts.

### Step 3: ISOs, start and migration
- **`proxmox.iso.path`** (default `/var/lib/cloudstack-iso`): one `dir` entry per cluster, `csiso-<uuid of the path>`, content `iso`, **`shared 1`**, created when missing like `csp-` (new client method; the token needs `PVEDatastoreAdmin` on `/storage`, as for `csp-`).
- **`isoVolume`**: over SSH on this node, inside `withMount` (read-only): bind-mount the ISO file onto `<path>/template/iso/cs-<first 16 characters of the SHA-256 of store:relative path>.iso` (`touch`, `mount --bind`, `mount -o remount,bind,ro`; skipped when it is a mount point already), `pvesm`-visible check, volume `csiso-...:iso/cs-<hash>.iso`. The attach itself stays an API call (`updateVmConfig`). Any file in the store works, so the config drive ISO (`configdrive/...`) takes the same path. The directory is unmounted when the bind is made: the bind keeps the NFS mount alive on its own and the mount goes with the last bind (to check on the lab, M7).
- **Detach**: eject as today; then, when no VM configuration of the cluster names the volume (`grep -l` over `/etc/pve/nodes/*/qemu-server/*.conf` over SSH), unmount the bind (which releases the NFS mount) and remove the empty file. A sweep of binds that no configuration names runs when the host connects.
- **Start**: the bind of each ISO drive is made (and checked) before the drives are written, so a start after a node reboot works. **An ISO whose mount or bind cannot be made fails the start with the reason** (the store, the file, the node, the text of the error) and says to detach the ISO and try again; KVM (`getPhysicalDiskFromNfsStore` throws while the disks are set up) and VMware (`configureIso` and `prepareSecondaryDatastoreOnHost` throw) also fail the start. Decided 2026-11-05.
- **`PrepareForMigrationCommand`**: the destination makes the mount and the bind of every ISO of the VM before CloudStack moves it (M3: the same path on every node).
- **Removed:** `isoVolume`'s `csi-` entries, `createIsoDirStorage`, and their tests.
- Unit tests and lab checks as for step 2, plus: attach and detach on a running VM, an instance restarted after a node reboot, migration both ways with an ISO and with a config drive, two VMs with the same ISO (one detach keeps the bind), the sweep.

## 8. Mount options of the secondary store

CloudStack gives no mount options for secondary storage: the image store has only the NFS version (`secstorage.nfs.version`, `NfsTO.getNfsVersion()`); `nfsmountopts` exists for primary pools only. KVM mounts the store through libvirt with the system defaults (`hard`). For Proxmox the plugin mounts with:

| Setting | Default |
|---|---|
| `proxmox.secondary.mount.options` (global, `Advanced`, dynamic) | `soft,timeo=30,retrans=2,nosharecache` |

| Option | Why |
|---|---|
| `ro` or `rw` | Set by the plugin, never by the setting: read-only for templates and ISOs, read-write for volume snapshots |
| `vers=<n>` | Set by the plugin from the store's `secstorage.nfs.version` when it has one |
| `soft` | A dead export gives an I/O error instead of waiting for ever; a `hard` mount leaves the processes that touch it unkillable and hangs Proxmox's daemons if they poll it (lab M4: with `soft`, `pvesm`, `qm` and the services stayed responsive while the server was blocked) |
| `timeo=30`, `retrans=2` | How long a request waits before it fails: 3 s per try and 2 retries; the lab measured **about 99 s** until a read of an uncached file returned the error with these values (M4). Shorter values fail sooner and risk errors on a slow or busy server |
| `nosharecache` | The kernel shares one mount between exports of the same server that lie below each other, and the options of the first mount win (lab VS8: the secondary export lies below the primary's); without this option `soft` and `ro` can be silently ignored or the mount refused |

The setting accepts a comma-separated list of: `soft`, `hard`, `nosharecache`, `noatime`, `nolock`, `timeo=<number>`, `retrans=<number>`, `nconnect=<number>`, `rsize=<number>`, `wsize=<number>`, `proto=tcp`. Anything else, `ro`, `rw` and `vers` included, is refused with a message that names the option, because the value reaches a root shell. An empty value means the system defaults (what KVM does). A change applies to mounts made after it; a mount that exists keeps its options until it is unmounted or the node reboots.
- **M7 pass (2026-11-05):** a store mounted in a unique directory (`/mnt/css-tmp-test1`, `ro,soft,timeo=30,retrans=2,nosharecache,vers=4.2`), one ISO file bound from it onto a scratch file, then the directory unmounted: `umount` gave no "busy", the bind still shows the NFS source and reads (`head -c 4M` gave 4,194,304 bytes), and unmounting the bind lowered the number of NFS mounts of the store by one, so the NFS mount lives with the bind and goes with it. This confirms the per-operation mount and the ISO bind of section 7.
