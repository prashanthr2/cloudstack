- **Config drive (userdata) on Proxmox, secondary and primary (open, 2026-11-05):** the config drive ISO is on secondary storage by default and on the primary pool with `vm.configdrive.primarypool.enabled` (`vm.configdrive.use.host.cache.on.unsupported.pool` and `vm.configdrive.force.host.cache.use` decide the fallback). To do: test userdata end to end with the default (ISO on secondary, attached by path after the secondary mount redesign; its path is `configdrive/...`, not `template/tmpl/...`) and with the setting on (the plugin must create the ISO on the primary pool, probably over SSH, and Proxmox must be able to attach it); the re-attach on `PlugNicCommand` is item 32.
- **Secondary storage mounts (fixed 2026-11-06, steps 1 to 3 of design-phase11):** volume snapshots, templates and ISOs all mount the store per operation over SSH with `soft` options (setting `proxmox.secondary.mount.options`), and no Proxmox entry mounts it, so a dead export cannot hang a node's own daemons. What is left: an ISO that is **attached** is a bind of an NFS file, so a guest that reads the CD while the export is dead gets an I/O error after about 100 s (lab M4); an old `css-<store>` entry or a `/mnt/css-rw-*` mount from the old code, if still on a node, stays `hard` until someone removes it (`pvesm remove`, `umount`) or the node reboots.
- **System VM patching: look for a simpler way now that there is an SSH login (open, 2026-11-05):** today the plugin patches an SSVM or CPVM through the guest agent and the API only (behaviour.md section 17, item 21): `agent.zip` (about 115 MB) is uploaded to a per-node `dir` storage entry `csp-<uuid>` as a zero-padded `cs-patch-*.iso`, attached to a reserved `ide2` CD drive, read in the guest with `head -c` from `/dev/sr0` and checked with SHA-512; the small files (`cloud-scripts.tgz`, `patch-sysvms.sh`) go as base64 pieces through the agent. The reasons were that a token cannot write to a node and the guest has no network at that point; with SSH to the node (`sudo`) the plugin can do things the API cannot. Ideas to check: write the payload straight to the node (no `csp-` storage entry, no storage upload API, no padding rule) and attach it by path with `qm set` (the same root-only attach as ISOs in design-phase11-secondary-mounts.md); build one small ISO with `genisoimage` or `mkisofs` on the node holding all three files, so the guest mounts it and copies them (no base64 pieces, no `head -c`); or write the files into the guest disk of a stopped system VM with `qemu-img`/`guestfs` (probably not, it changes the template's disk). Keep: patching only when the signature differs, the checksum of what was copied, the CD emptied afterwards. Also decide whether the `csp-` entry should go, as the secondary store entries do. To measure first: the time of the current method for a 115 MB `agent.zip` and a CPVM start, so that a change has to beat a number.
- **Linked clones for root volumes (parked 2026-11-05):** design-phase12-linked-clones.md. A setting `proxmox.create.full.clone` of scope StoragePool (so at pool, cluster, zone and global level, like VMware and XenServer; KVM has only a host property `create.full.clone`), the offering's provisioning type deciding first as on KVM (thin may be linked, sparse and fat are full copies), a template VM per template and pool made at the first linked deploy, and the short volume path kept in CloudStack. To build after step 2 of design-phase11 and a lab spike (LC1 to LC10); not started. Decisions still open: the default of the setting, and what to do with a volume bigger than its template (KVM grows the overlay, VMware forces a full clone).
- **Application-consistent snapshots (open, decided 2026-11-04 to stay crash-consistent for now):** volume snapshots and instance snapshots without memory of a running instance are crash-consistent, as if the power was cut at that instant. Making them file-system or application consistent needs the QEMU guest agent: the guest runs `qemu-guest-agent` and the VM has `agent=1` (the plugin sets it only for system VMs, `ProxmoxVmConfig.java`), then the guest's file systems are frozen around the snapshot (Windows: VSS, so VSS-aware applications are consistent; Linux: scripts in `/etc/qemu/fsfreeze-hook.d/` written by the guest admin). Core gives no switch (`SnapshotManagerImpl` sets `quiescevm` to false for volume snapshots), so it would be a plugin setting. Still to find out on the lab: whether Proxmox freezes by itself for a snapshot without memory when `agent=1` (task log shows `guest-fsfreeze-freeze`) or the plugin has to call the agent API (`fsfreeze-freeze` and `fsfreeze-thaw`) around it. Decisions for later: freeze only when the agent answers a ping, with a thaw in `finally`; on a failed freeze continue crash-consistent with a log warning (proposed); how `agent=1` gets onto user VMs (a VM setting or template flag; not on all, because a VM without the agent can wait on agent timeouts at shutdown).
- **Honour `quiescevm` on instance snapshots (open, narrower way into the item above; 2026-11-04):** KVM adds libvirt's `QUIESCE` flag when the instance snapshot of a running instance asks for it (`LibvirtCreateDiskOnlyVMSnapshotCommandWrapper`), which freezes the guest's file systems through the guest agent, and **fails** with "QEMU guest agent is not connected" when there is no agent (no silent fallback). Application consistency then depends on the guest (Windows VSS, or scripts in `/etc/qemu/fsfreeze-hook.d/` on Linux). The Proxmox plugin ignores `VMSnapshotTO.getQuiescevm()` today. Proposal: when the flag is set, freeze through the agent around the Proxmox snapshot, thaw in `finally`, and fail with a clear message when the agent does not answer; the user opts in per snapshot, so no need to put `agent=1` on every user VM or to decide between failing and continuing. Needs the lab check first (does Proxmox freeze by itself for a snapshot without memory when `agent=1`, or must the plugin call `fsfreeze-freeze` and `fsfreeze-thaw`; and the agent API may need `agent=1` in the VM config). Core gives no quiesce flag for volume snapshots (`SnapshotManagerImpl` sets `quiescevm` to false), so this covers instance snapshots only; a volume snapshot of a running instance (a VM snapshot underneath) stays crash-consistent.
- **A template VM is on one node; clones from it need that node (open, 2026-11-05, TV6 question):** a template VM's configuration is on the node whose agent made it, and Proxmox runs a clone on that node (the plugin asks for `target` = the deploying node, so the new VM is made where the instance runs, and no template is copied or moved). If that node is down or in maintenance, deploys from templates on it fail until it is back. Possible fixes (to try on the lab): migrate the template VM to an online node (templates on shared storage can be migrated offline) when the clone is refused, or always make template VMs on a fixed node.
- **Many clones at once on one pool (open, 2026-11-05, TV10):** 2 of 10 parallel full clones failed with `cfs-lock 'storage-<pool>' error: got lock request timeout` (Proxmox's cluster lock on the storage while it allocates a disk). The plugin now tries such a clone again with a new VM id (up to 10 times); if that is not enough on a busy pool, limit the clones that run at once per pool. Linked clones (design-phase12) make a clone a small file, which also removes the cost and most of the contention.
- **Clone times and the pool (measured on the lab 2026-11-06, TV10):** from the Proxmox task list, clones that ran with little else going on took 22 to 26 s each (one took 77 to 82 s), and ten parallel clones of a 100 GiB template on one NFS pool took 205 to 243 s each, with two failures (`cfs-lock ... got lock request timeout` after 11 s, and `unable to create image: ...-locked command timed out` after 70 s). Parallel deploys do not go faster than one after another: the pool's I/O is the limit. The retry of both lock errors is in; linked clones are the real fix (above).
- **ISO binds left by a delete that reached another node (open, 2026-11-06, IS5):** core sends the delete of a root volume to a random host of the pool, and the agent can only log in to its own node. The bind on the VM's node is removed by the sweep at the next ISO command (attach, start with an ISO, migration) on that node, or when the agent restarts. A login to the VM's node (its address is known from the cluster node list) would remove it at once.
- **A stopped instance's ISO is bound until it starts again or is deleted (open, 2026-11-06, IS4):** a detach of an ISO from a stopped instance never reaches the host; the config keeps the drive and the bind until the next start rewrites the drives.
- **The start of a VM that was created on another node (open, 2026-11-06):** about (N-1)/N of the deploys on N nodes need the offline move of the configuration (`qm migrate` of a stopped VM) before the start, because core makes the volume on a random host. The move uses Proxmox's node-to-node SSH and checks the storages on the target, so one node with a broken inter-node key or an inactive entry fails every deploy that lands there, and the failure is now named in the start answer. Alternative if that is not enough: move the configuration file over SSH (`mv /etc/pve/nodes/<from>/qemu-server/<id>.conf /etc/pve/nodes/<to>/qemu-server/`), which needs no inter-node SSH and no storage check.
- **Template from a volume snapshot (open, decided 2026-11-08, design-phase11-step4-template-from-volume.md section 4):** core sends the command to the secondary storage VM, whose code (`NfsSecondaryStorageResource.copySnapshotToTemplateFromNfsToNfs`) only handles snapshots of hypervisor type KVM or XenServer and answers an empty failure for Proxmox. Workaround, once the volume part of step 4 is built: create a volume from the snapshot, then a template from that volume. Real fix: let that method treat `Proxmox` like `KVM` (one line, separate core change), effective only after the system VM template is rebuilt.
