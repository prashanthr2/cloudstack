## Known limits (not bugs; confirm they are acceptable)

| # | Limit | Notes |
|---|---|---|
| 6 | **A console session is single use** | A reload or a dropped connection needs "View console" again (seen once on 2026-10-20: "disconnected", then it worked). The API token secret is inside the console proxy token |
| 7 | **A stale instance page lets you click "Console" on a VM that is already stopped** | CloudStack answers "must be running to connect console"; correct behaviour. The state of an out-of-band stop reaches CloudStack within one `ping.interval` (60 s) |
| 8 | **ISO storage entries (`csi-...`) are kept after use** | One per different ISO ever attached; no cleanup. Removing unused ones needs a scan of the VMs' configurations. The per-account template entries (`cst-...`) and the per-account `dir` entries are in the same situation |
| 9 | **A CD-ROM drive cannot be added to a running VM** | Proxmox keeps it pending until a restart. VMs started before the ISO build have no drive: one stop and start fixes it. Raising `vm.iso.max.count` needs a restart of the VMs too |
| 10 | **Bridges are not created on the destination of a migration** | The administrator keeps the bridges identical on all nodes; preparation refuses a destination that lacks one |
| 11 | **CloudStack does not set Proxmox's HA maintenance mode** | No REST endpoint (lab L8); run `ha-manager crm-command node-maintenance enable <node>` on a node if Proxmox HA must also avoid it |
| 12 | **TLS: only "verify against the Java truststore" or "do not verify"** | No certificate pinning |
| 13 | **A detached data volume cannot be resized** | Proxmox has no resize for a disk that no VM uses; the volume must be attached first. A shrink is refused (CloudStack itself refuses it for QCOW2) |
| 14 | **The vmids 900000001 to 999999999 are reserved for CloudStack** | They own the data volumes (`900000000 + account id`). A VM with such an id, destroyed with the "destroy unreferenced disks" option of the Proxmox UI, would remove that account's volumes. Documented; the plugin refuses to create a VM in that range |
| 15 | **A SATA data disk cannot be attached to or detached from a running instance** | Proxmox cannot hot-plug it: attach or detach while the instance is stopped. SCSI and VirtIO work live |
| 16 | **Proxmox deletes an image that a VM still refers to** | The plugin deletes a data volume's image only when CloudStack asks (it only does so for a detached volume); nothing in the plugin checks the VM configurations |
| 17 | **Data volumes cannot be copied, snapshotted, uploaded, downloaded or moved to another pool yet** | Answered with "not supported for Proxmox yet". Proxmox itself can move a disk to another storage (`move_disk`) and migrate a running VM with its local disks (`with-local-disks`, `targetstorage`); the plugin does not handle CloudStack's storage migration commands yet. When it does, the capability row (`storage_motion_supported`) and `VmStorageMigration` should be set for Proxmox |
| 18 | **`dataDiskController` and `rootDiskController` are read-only for regular users** | The global setting `user.vm.readonly.details` makes them admin-only by default; remove them from it if users should set them |
| 28 | **Security groups are not supported** | The capability is off for Proxmox, so a network with security groups cannot be used. Proxmox has its own VM firewall; mapping CloudStack's rules to it is not started. `PlugNicCommand` applies no security group rules |
| 29 | **Site-to-site VPN and remote access VPN are not tested** | The VPN commands are scripts run in the router through the guest agent (the same way as the other router commands), so they may work, but no run was made on the lab. Not part of 8b or 8c |
| 30 | **Private gateways (VPC) are not tested** | A private gateway is another interface plugged into the VPC router (`PlugNicCommand` and `IpAssocVpcCommand`, which are implemented); one with a VLAN of its own, its ACLs and static routes were not run on the lab |
| 31 | **Redundant routers (VRRP) are not tested** | Nothing prevents them, but a pair of routers on different Proxmox nodes was not run. Not part of the design |
| 32 | **The config drive is not re-attached when an interface is plugged into an instance** | KVM detaches and attaches the config drive ISO again on `PlugNicCommand` for a user VM; the Proxmox plugin does not, so metadata that depends on the NIC list is not refreshed until the next start |
| 33 | **Load balancing by the router was not run; the internal load balancer VM, Kubernetes (CKS) and shared file system VMs were not tried** | The router's load balancer is a script run in the router like the other rules; the other VM types are system VMs that the start path of section 17 should handle, but none was run |
| 34 | **VM and volume statistics are answered "unsupported"** | `GetVmStatsCommand`, `GetVmDiskStatsCommand` and `GetVmNetworkStatsCommand` (CPU, memory, disk and network usage of VMs) are not implemented for Proxmox; the router's own traffic counters are |
| 35 | **The first start of a new SSVM or CPVM on another node can fail once** | Same as open issue 24: the disk made on one node is not yet visible on the node that starts the VM (NFS caching); core retries on another host |
| 36 | **VPC traffic statistics are empty (system VM scripts)** | `vpc_netusage.sh -l <public ip> -g` prints nothing in a VPC router: its create option exits without making rules and nothing else creates the `NETWORK_STATS_<dev>` chain it reads, so `NetworkUsageCommand` for a VPC always reports 0 bytes. Seen on the lab 2026-10-25 with a few pings; read in the scripts of this branch, so most likely the same on KVM (not run there). The fix is in `systemvm/debian/opt/cloud/bin` (make the chains for the public interface of a VPC router), not in the plugin |
| 37 | **A router, the SSVM or the CPVM cannot be migrated to another host (`migrateSystemVm`)** | Seen on the lab 2026-10-25 (VPC router): core requires the hypervisor to claim `VmStorageMigration` and the storage motion capability of its exact version (`hypervisor_capabilities`, the Proxmox row has `storage_motion_supported` 0) before it finds out that no volume has to move; see upstream note 26. Decision: no change to core for this; revisit with the storage migration of the plugin (item 17: `move_disk`, `with-local-disks`), when the capability row and the functionality are set for Proxmox. Workaround: stop and start the system VM or router on another host (a router: restart the network with cleanup). User instances migrate (Phase 5). `prepareNicForMigration` already treats Proxmox routers like KVM ones (8b), so their hot-plugged interfaces are covered once a migration is possible |
| 38 | **`PatchSystemVmCommand` and `SetHostParamsCommand` are not implemented** | The "patch system VM" API and the check after a management server upgrade answer "unsupported" for a Proxmox system VM; patching happens at every start only. The code of the start (`ProxmoxSystemVms`) can be reused. Decide whether an upgrade by restarting the system VMs is enough |
| 39 | **No warning at a later connect when the control bridge has disappeared** | Designed (design-phase8 4.7 step 5) but not built. A start of a system VM on that node fails with a clear message, so the effect is a later failure instead of an early warning |
